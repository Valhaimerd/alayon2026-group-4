# Account settings and optional MFA

Confirmed 12 November 2026: MFA enrollment is optional for all account roles. Accounts can enable SMS codes delivered directly through HaturikoSMS, an authenticator app through Supabase TOTP, or both. An enabled account must verify one configured method before private workspace access. SMS verification does not use the paid Supabase phone-MFA service.

Sign-in is account-neutral and uses the same email/password form for every account. The explorer header's circular profile button opens **Account settings**, including display name, password changes, verification methods and sign-out. Passwords require at least eight characters and matching confirmation. Sign-in email, official instructor name/code, and access roles remain administrator-managed. A display-name edit never grants a role or changes an official instructor record. General sign-in does not grant scheduling privileges or introduce self-registration.

Authenticator setup offers a QR code and a manual setup key. MFA becomes active only after a valid six-digit code. Closing unfinished setup leaves an unverified factor; starting setup again replaces it. On subsequent sign-in, enrolled accounts see a verification dialog before private data loads. SMS users choose **Send login code**; users with both methods may select either. Multiple existing TOTP factors can be selected. Users who lose their verification method must contact the administrator; self-service recovery codes and email/password recovery are not implemented.

SMS setup accepts international numbers and normalizes Philippine `09…` and `63…` formats. Entering a number never enables MFA until its code is verified. Codes expire after five minutes, permit five failed attempts, are invalidated after use or resend, and are tied to the requesting account and Supabase session ID. Resends require 60 seconds, with at most ten requests per account per UTC day. Provider failures also count toward these limits. A verified SMS session lasts twelve hours or until that sign-in session ends. Numbers are masked outside the enrollment input. Turning off SMS or changing the verified number removes existing SMS verifications. A valid delivered challenge resumes after refreshing the page, without sending another message; its ID and masked destination are exposed only to its requesting session.

Server actions validate the authenticated user and database MFA status. Password verification uses an isolated client to preserve the current session's MFA level. The `optional_account_mfa` migration adds restrictive policies to private scheduling tables and account roles. The subsequent `account_sms_mfa` migration extends `account_mfa_verified` with SMS session checks. The shared `has_role` function enforces both methods for security-definer RPCs and views as well. Public published schedules remain available. Apply migrations in order, after the academic account-role migration. SMS verification protects the application's private data; it does not produce a Supabase AAL2 token or change Supabase Auth's native account-management endpoints.

## Server configuration and RPC contract

Set `HATURIKOSMS_API_KEY` and a cryptographically random, server-only `ACCOUNT_SMS_SERVER_SECRET` of at least 32 random bytes in each deployed environment. Provision the SHA-256 hex digest of the latter in `private.account_sms_config.secret_hash` through trusted database access. The connected project and local environment are configured. Deployments must receive the same server secret; never expose it through a `NEXT_PUBLIC_` variable. Rotating this server credential requires updating the database digest and server environment together. `HATURIKOSMS_SEND_ENABLED` controls schedule-change notices only; it does not disable login codes.

The private schema is inaccessible to browser roles. Authenticated server RPCs `start_account_sms`, `account_sms_delivery`, `verify_account_sms` and `disable_account_sms` require both the current account/session and the server credential. Clients cannot mint or verify their own challenges through direct API calls. Codes are generated using Node's cryptographic random-number generator and stored only as HMAC-SHA256 hashes bound to the user and challenge ID. Code hashes, full phone numbers and the server credential are never returned by server actions. `account_sms_status` returns only the current user's enabled state and masked phone number. This is an additive RPC contract; existing scheduling RPC signatures are preserved.

`start_account_sms` returns `{ok:true,phone}` to the trusted server, or `{ok:false,reason}` for `cooldown`, `daily_limit`, `verify_first` or `not_enabled`. Only provider-accepted challenges are marked delivered. `verify_account_sms` returns `{ok:true}` or `{ok:false,reason:"incorrect"|"expired"}` without throwing on a wrong code, so failed-attempt increments commit. Settings mutations require a verified account when MFA is already enabled. An invalid server credential raises insufficient privilege. The browser receives actionable messages, a challenge ID and a masked destination, with no provider error bodies or internal database details.
